# Formal verification of Obsidian Agent

## Summary

Use Lean 4 to verify small, consequential parts of `plugins/agent`: guarded note replacement, chat run ownership, MCP registration and connection ownership, lexical path restrictions, and recovery of interrupted chats. Start with guarded note replacement and require evidence that the model matches the packaged plugin before expanding the proof surface.

This plan includes planner-authored Lean model kernels and proofs; the wider plugin verification work is proposed. It follows [0001](../0001-initial-plan.md) and the repository's [Lean Verification](../../../../.agents/skills/lean-verification/SKILL.md), [E2E Testing](../../../../.agents/skills/e2e-testing/SKILL.md), and [QA Methodology](../../../../.agents/skills/qa-methodology/SKILL.md) guidance. Source and existing tests were inspected at `e4027547feb0e09b0e5fd759b4b917aa70aa0784`; the initial planning pass inspected source only. The subsequent Lean checks and exact proof scope are recorded in [Current Lean evidence](#current-lean-evidence); desktop correspondence is sampled by the independent packaged-plugin scenarios recorded below.

Keep the runtime in TypeScript. Lean will establish properties of explicit models; deterministic desktop E2E scenarios will supply evidence of agreement with production behavior. Neither finite agreement nor a model proof establishes full correctness of the plugin, Obsidian, pi, MCP transports, or storage.

## 1. Guarded note replacement

### Contract and model

The user-visible requirement is that an agent cannot replace a note whose current disk content differs from the content it knows for that path. A rejected edit reports an error and causes no replacement by that operation. An intended valid edit must succeed when its guards and the write succeed.

Accept string `path` and `content` arguments, a path accepted by the existing note policy, and an existing `TFile`. A snapshot comes from a successful read, creation, or earlier replacement in the same tool instance; attachment text, search excerpts, and previous chat turns do not establish one. An empty snapshot is present content, distinct from no snapshot.

Define `GuardedEdit` with a map from canonical paths to optional content, disk observations, an editor observation, and an edit operation that captures its path, snapshot, and replacement. Use opaque content with decidable equality for the proof. At the executable boundary, encode content as UTF-16 code units so equality preserves and reflects JavaScript `===`, including empty strings, line endings, combining characters, and lone surrogates. Model a relevant editor observation as no matching editor, matching editor with unavailable text, or matching editor with text; the latter two must reflect the current optional editor API behavior.

Split the operation into snapshot capture and editor observation, the disk comparison and write inside `vault.process`, and promise completion with snapshot update. External disk and editor changes can occur between these stages. The disk transaction is the only assumed atomic stage. Model read failure, missing file, process failure, unload, and an already issued operation completing after cancellation. A fresh tool instance starts with no snapshots.

| Condition at the relevant stage                                                 | Observable result                 | Effect owned by this operation                                                                         |
| ------------------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Invalid arguments/path or missing file                                          | Rejection                         | No replacement; no snapshot update.                                                                    |
| No remembered snapshot                                                          | Read-required rejection           | No replacement; no snapshot update.                                                                    |
| Matching active editor has unavailable text or text different from the snapshot | Editor conflict                   | No replacement; no snapshot update.                                                                    |
| Disk text inside the transaction differs from the captured snapshot             | Disk conflict                     | No replacement; no snapshot update.                                                                    |
| Snapshot and guards match, and process succeeds                                 | Success reporting the edited path | Commit the replacement and, on successful completion, remember that replacement.                       |
| Process rejects because of I/O rather than a guard                              | Effect failure                    | Do not report success or advance the snapshot. A generic I/O failure does not establish disk rollback. |

Prove these public obligations over the model:

- **V1 — guarded commit:** every replacement committed by this operation had a present snapshot equal to the disk text observed inside that transaction.
- **V2 — rejection preserves state:** a guard rejection makes no disk or snapshot change attributable to this operation. External actors may still change the note.
- **V3 — useful success:** a present matching snapshot, accepted path, existing file, passing editor observation, and successful process outcome permit replacement, including an empty original or replacement.
- **V4 — snapshot update:** successful completion records the committed replacement for that path; another path's snapshot is unchanged. The disk may change again after the commit.
- **V5 — failure discipline:** an unsuccessful read or edit does not invent a successful snapshot update. Distinguish a known failure before commit from an I/O failure whose disk outcome is unknown.

Assume sequential operations within one tool instance, as configured by `send` and `edit_note`, and verify that boundary with the real tool runner. Other tool instances and external writers may interleave at the disk transaction boundary. If implementation work permits concurrent operations on one snapshot map, expand the model before claiming V4 or V5.

### Counterexamples and limits

Preserve these cases as explicit model inputs and implementation scenarios where observable:

- No snapshot with an empty disk must reject; a present empty snapshot with an empty disk can succeed. Treating both as false is incorrect.
- Read `A`, observe an external write of `B`, request `C`: reject and retain `B`. Moving the comparison before the transaction admits a write between comparison and commit.
- Read `A`, external writes `B` and then `A`, request `C`: content equality permits the edit. A claim that no intervening edit ever happened is false without revision tracking.
- Read `A`, pass the active editor check, then change the editor before the transaction; or edit a non-active pane. The current guard does not establish preservation of all unsaved buffers.
- Abort after a vault operation has started: the current tools do not inspect a cancellation signal. Stop does not establish rollback or prohibit completion of that operation.

The pinned Obsidian typings describe `Vault.process` as an atomic read/modify/save with a synchronous callback. Treat that API contract, including no replacement when the guard callback throws, as an environmental assumption to exercise in desktop E2E. Do not extend it to arbitrary adapter failures, outside filesystem writers, rename/recreate identity, or all editor buffers. Broader editor synchronization and revision-based conflict detection require their own written contracts before implementation.

## 2. Chat run ownership

Specify a `RunOwnership` transition system with selected chat, per-chat history and status, one optional current owner `(pluginEpoch, runId, chatId)`, and phases `preparing`, `saving`, `streaming`, `cancelling`, and `finished`. IDs and time are explicit inputs; freshness is a precondition enforced by the allocator, not a consequence of using UUIDs or unbounded Lean numbers.

The proposed behavior extends the existing streaming guard to the entire accepted send:

- **R1 — one owner:** accept a nonempty send with a selected model only when no run owns the plugin. Reserve ownership synchronously before skill loading or persistence can suspend. A second send cannot start a provider request while the first owns preparation, saving, streaming, or cancellation.
- **R2 — event isolation:** only events carrying the current epoch and run identity may update its partial text, error, messages, activity, pending status, or owner. Chat identity alone is insufficient when consecutive runs share a chat. Ignore events from a finished or superseded run.
- **R3 — cancellation and switching:** Stop, chat switch, new chat, and unload invalidate pending work before it can start another provider request or publish callbacks. Capture model, thinking, attachment, chat, and enabled skill selection for the accepted send. Finalize the owning chat as interrupted before allowing a new owner; already issued external effects follow their separate contracts.
- **R4 — failure and useful completion:** skill loading, saving before a prompt, and provider failure terminate the owning run with an observable error and release ownership. An accepted send whose dependencies succeed starts exactly one prompt and can save a completed reply. A persistence failure is reported without claiming the history was durably stored.

Include events at every actual suspension point: skill read success/failure, save start/success/failure, provider start, message/tool events, provider error/end, abort request/acknowledgement, switch, unload, and reload. Late events remain possible after abort. Separate ownership invalidation from physical provider termination; liveness requires dependency termination and fair scheduling and is not part of R1–R4.

Prove the invariant for the initial state, preservation by every permitted transition, and consequently every reachable trace. Try `send A → skill read pauses → send B`, `send A → save pauses → switch chat`, and `old run ends → new run starts in the same chat → delayed old callback`. These are source-derived counterexample candidates, not desktop reproductions collected by this plan. Preserve the failing traces before adding run tokens or changing lifecycle code.

Cancellation policy for implementation and E2E: an accepted send interrupted during preparation leaves no invented assistant reply. Once streaming begins, text already shown to the user remains visible in that chat after Stop, switch, or unload and after reload; later output from that run is ignored. The chat is marked interrupted, its pending flag is cleared, and a new send may start without waiting for a stalled preparation or transport. The retained partial text is history for display, not evidence that the model completed its reply. The current Lean ownership kernel does not prove this history projection; retain R3 as pending until the implementation and desktop trace establish it.

## 3. MCP registration and connection ownership

### Registration and routing

Define `McpRegistry` as a partial mapping from an exposed name to its original `(serverId, toolName, connectionGeneration)`. Inputs are ordered enabled server configurations and their advertised tool lists. Include the reserved built-in tool names and the supported provider name alphabet and length bound; confirm those limits against the pinned provider adapters during implementation.

The current naming expression is not injective: server IDs `a-b` and `ab`, both advertising `ping`, produce `mcp_ab_ping`. Tool names `a-b` and `a_b` also collide within one server; shared prefixes longer than the 12-character server or 40-character tool truncation have the same problem.

Use an explicit rejection policy: a newly registered name that is already occupied is rejected with a visible server/tool error and preserves the existing registration. Process candidates in a recorded deterministic order, and reject duplicate server IDs before connecting. Do not silently overwrite, dispatch to the first arbitrary match, or assume hash collision freedom. Independent non-colliding tools must still be usable. If a different naming policy is chosen, revise this contract and its independent test oracle first.

Duplicate-ID rejection counts every configured server row, including disabled rows. No row with that ID connects until the duplicate configuration is removed; the visible error names the duplicate ID condition.

- **M1 — unique registration:** successfully published names are unique across MCP servers and built-in tools and satisfy the declared provider constraints.
- **M2 — correct dispatch:** resolving a published name selects exactly its recorded original server/tool pair and current connection generation; an absent, rejected, or invalidated registration cannot dispatch.
- **M3 — useful registration:** a valid non-colliding candidate is accepted; rejection leaves existing entries and their dispatch targets unchanged.

Production registration and execution must use the same mapping or an equivalent checked association. Model an active agent retaining a tool object after its connection is invalidated; the call must reject rather than use a stale registration. Observe actual receiving servers in E2E, as uniqueness of strings alone does not establish correct routing.

### Connection lifetime

Define `McpLifecycle` with a plugin epoch, desired configuration revision per server, pending connection attempts, published connections, and disposal obligations. Give each attempt a fresh ownership token. Include connect/list-tools success and failure, repeated sync, disable, re-enable, configuration replacement under the same ID, close success/failure, and unload.

- **M4 — current publication:** only an attempt matching the live plugin epoch and current enabled configuration may publish tools or errors. Stale success schedules disposal; stale failure cannot overwrite the current server's status.
- **M5 — removal:** disable, replacement, and unload remove the old connection's registrations immediately and request close. A late completion cannot repopulate them. At most one generation per server is published.
- **M6 — useful connection:** a still-current enabled attempt whose connection and discovery succeed can publish its non-colliding tools.

Prove initial validity, transition preservation, and reachable-trace invariants. The minimal counterexample candidate is `enable → connect pauses → disable/unload → connect and listTools finish`; current `sync` can reach publication without checking whether its attempt is still wanted. Also model two concurrent syncs and a configuration edit during connection. Close requests are safety obligations; eventual process/transport closure depends on the external client and must be checked separately with controlled fixtures.

## 4. Lexical paths and skill discovery

Define `VaultPaths` separately from content and effects. Preserve the existing accepted language: reject absolute paths, ASCII drive prefixes, backslashes, dot-prefixed segments (including `.` and `..`), and a suffix other than case-insensitive `.md`. Repeated `/` separators are accepted only when Obsidian normalization equals collapsing those separators. Do not add an ASCII-only restriction or silently reject valid Unicode paths to simplify the proof.

- **P1 — accepted paths:** any accepted canonical path is relative, has no forbidden segment, and has a Markdown suffix. Canonicalization is idempotent on accepted paths, and allowed repeated-separator aliases identify the same snapshot key.
- **P2 — skill containment:** a discovered skill has filename exactly `SKILL.md`, no dot-prefixed segment, and lies below a nonempty normalized configured folder on a segment boundary. `Skills-extra/SKILL.md` is not beneath `Skills`; `Skills/Writer/SKILL.md` is. An empty folder does not mean the whole vault.
- **P3 — useful acceptance:** ordinary nested Markdown paths, permitted Unicode names, uppercase Markdown extensions, and ordinary nested skills are accepted under the stated rules.

Model string operations over UTF-16 code units or justify each abstraction. Obsidian normalization and file lookup remain explicit boundaries; compare the chosen normalization model against real calls through the tool and skill UI. Lexical containment does not prove physical filesystem containment, symlink handling, case equivalence, or that two distinct paths cannot alias through an adapter. Full proof of arbitrary Unicode case conversion is unnecessary if only the ASCII Markdown suffix is relevant and that reduction is justified.

## 5. Restoration and persistence

Define `RestoreState` over explicit JSON values and the deterministic restoration projection. Model time and fresh IDs as supplied inputs. Cover the schema fields needed for chat selection and `pending`/`interrupted` status; treat message payloads as opaque preserved values until a separate complete message schema is specified.

- **D1 — interrupted restoration:** every saved pending chat restores with `pending = false` and `interrupted = true`; otherwise preserve its interruption flag and retained history.
- **D2 — usable selection:** after restoration an active chat exists. Preserve an existing valid selection; when none exists, create and select a fresh empty chat as the current `onload` does. For a well-formed state with unique IDs, preserve uniqueness.
- **D3 — stable restoration:** applying restoration again to its repaired output makes no further changes, with explicit freshness/time inputs and no intervening events. Scope this to restoration; do not claim unrestricted `parseData` idempotence while it generates IDs and timestamps.
- **D4 — ordered persistence:** model the existing queue reading current data at save start, not snapshots captured when `persist()` is called. Only one save executes at a time; a rejected save does not permanently prevent a later save attempt. A successful save records the state supplied to that save under the storage API contract.

Test seeded pending data with a real reload, missing active IDs, valid-history preservation, save failure followed by a later successful save, and reload from the last successfully written data. Do not claim that an interrupted or failed write is crash-atomic without a storage guarantee.

An input such as an assistant message with only a `role` passes the current role filter; duplicate chat IDs also survive parsing. The load policy below closes those implementation gaps, while the current typed Lean restoration model does not prove arbitrary-input message validity or ID uniqueness. JavaScript timestamps can be non-finite when supplied directly even though JSON has no such number literals; any numeric invariant needs a guarded finite, representable input domain.

Load policy for implementation and E2E: retain the first chat with each nonempty ID; assign a fresh unused ID to every later duplicate or empty-ID chat while preserving its order and history. A saved active ID selects its first occurrence. Drop messages whose required role-specific payload is malformed, preserving valid messages in their original order. A malformed message must never enter the provider request. These decoder rules extend the typed restoration model's input boundary; no existing theorem proves them.

### Representation and environment assumptions

- Content and lexical path operations use lists of `UInt16`; fixture JSON preserves their numeric code units. Disk encoding of lone surrogates is not assumed lossless. Those cases establish model equality behavior until a desktop boundary scenario supplies evidence.
- Chat IDs and snapshot-map keys are opaque Lean strings. The production mapping must preserve and reflect equality; do not assume an arbitrary JavaScript string can be converted to Lean text without checking its encoding.
- Token epochs/serials and configuration revisions are explicit symbolic natural-number inputs. Production allocation must avoid reuse; production uses a per-instance epoch object and `bigint` run serial, whose equality mapping is reviewed in TypeScript but is not proved in Lean. The save queue's natural number counts pending operations in the model; it does not verify JavaScript arithmetic.
- Guarded editing assumes sequential operations within a tool instance and correct pairing of its commit and completion. Obsidian atomic read/modify/write and callback-rejection semantics are outside Lean. An external edit after commit may change the disk again.
- Chat and MCP transitions permit delayed events. The proposed rules require production checks at the actual suspension points. External promises, storage, and transports are not assumed eventually to succeed.
- Typed restoration preserves only the projected fields. Malformed JSON, arbitrary message validity, and UUID allocation require a separate decoder-to-projection proof; desktop tests sample repaired IDs and rejected malformed payloads.
